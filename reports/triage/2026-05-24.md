## Known-Bug Status

### 1. OAuth / field-level-security failure on custom Salesforce field

**Status: Still present (no specific handling).**

`primeqa/execution/executor.py` builds a bare `SalesforceExecutionClient`
(lines 29–41) and sends create/update payloads directly to the SF REST API.
When SF rejects a field write due to FLS (e.g.
`INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY` or `INVALID_FIELD_FOR_INSERT_UPDATE`),
the response is recorded verbatim in `run_step_results.api_response` and the
step is marked `failed` — no retry, no field-strip logic, no explicit error
code routing.

The executor does have one related mitigation: `name_createable_lookup`
(line 188) skips auto-injecting the PQA_ name prefix on objects where `Name`
is not createable, preventing a specific class of `INVALID_FIELD_FOR_INSERT_UPDATE`.
But this is Name-only; arbitrary custom field FLS errors fall through to the
generic failure path.

`primeqa/intelligence/service.py:148` and `primeqa/intelligence/service.py:335`
classify `FIELD_CUSTOM_VALIDATION_EXCEPTION` for the agent triage taxonomy, but
this is the triage/analysis layer, not the executor. No runtime retry or
field-strip on FLS denial exists anywhere in the execution path.

**Relevant files:** `primeqa/execution/executor.py:43–46` (create_record),
`primeqa/intelligence/service.py:148, 335` (triage taxonomy only).

### 3. Test cases incorrectly showing "draft" status

**Status: Narrow live path; not systematically fixed.**

`TestCase.status` is set to `"draft"` on creation
(`primeqa/test_management/service.py:210, 341, 737, 763`;
`primeqa/test_management/repository.py:298`). Promotion to `"approved"` happens
in `submit_review` when the BA reviewer approves:

```python
# primeqa/test_management/service.py:1416–1424
if status == "approved":
    tcv = self.test_case_repo.db.query(TestCaseVersion).filter_by(
        id=review.test_case_version_id,
    ).first()
    if tcv:                                  # ← silent skip if None
        self.test_case_repo.update_test_case(
            tcv.test_case_id, review.tenant_id,
            {"status": "approved", "visibility": "shared"},
        )
```

The silent `if tcv:` guard means that if a `BAReview` row has a NULL or
stale `test_case_version_id`, the approval is recorded but the TC status
never flips from `"draft"`. The review succeeds (200 back to the caller)
with no indication that the TC was not promoted. This is a silent failure mode.

Additionally, the `reason` parameter received by `submit_review` (line 1408)
is never passed to `review_repo.update_review` (line 1410–1411) — only used
for the rejected-feedback signal. Depending on whether `BAReview` has a
`reason` column, this could silently discard a rejection reason. Not directly
related to draft-status stickiness but worth noting.

**Relevant files:** `primeqa/test_management/service.py:1416–1425`,
`primeqa/test_management/models.py:101, 125`.

### 4. Test Suite dropdown not populating (suspected environment_id mismatch)

**Status: Design-level gap; no code bug in current implementation.**

The suite dropdown on `/run` (Mode C) is **server-rendered** via Jinja2:

```html
{# primeqa/templates/run/index.html:220–228 #}
<select id="suite-id" onchange="PrimeQA_onSuiteChange();">
  <option value="">— pick a suite —</option>
  {% for s in suites %} … {% endfor %}
</select>
```

The `suites` variable is populated by `run_page()` in `primeqa/views.py:784–804`,
querying all non-deleted suites for the tenant — no `environment_id` filter.
If the dropdown appears empty, the tenant has no suites (deleted or never created).

The `onEnvChange()` JS handler (`run/index.html:466–482`) resets and re-loads
Sprint, Tickets, and Release state when the environment picker changes, but does
**not** reset or reload the Suite picker. Suites are tenant-scoped, not
environment-scoped, so this is intentionally omitted — but it means the
"environment_id mismatch" suspicion is likely tracking a symptom of something
else (e.g., suites existing in a different tenant, or the user lacking
`run_suite` permission).

The `show_suite` flag in the template (`run/index.html:61`) is gated on
`has_permission('run_suite')`. Users without the `tester` or `admin` role who
have only `run_single_ticket` will see the Suite tab absent entirely, which could
look like "not populating." The `run_suite` permission is wired to `tester` and
`admin` roles in `primeqa/core/permissions.py:176, 199`.

The `/api/suites/:id/overview` endpoint (`primeqa/execution/routes.py:705–750`)
does not accept or use `environment_id`; last-run lookup is tenant-wide for the
suite (line 737–748), which could cause a stale cross-environment run to appear.

**Conclusion:** No code-level bug found matching the "environment_id mismatch"
description. Most likely symptoms are: (a) tenant has no suites created,
(b) user lacks `run_suite` permission, or (c) last-run display showing
a run from a different environment is confusing the reporter.

### Grounded negative test generation

All work on grounded negative test generation is **design-only** (Substrate-3,
Theme 4, decisions D-083 and D-084, committed May 20 as docs). There is no
runtime Python implementation.

The existing runtime implementation of negative tests is the `expect_fail` flag
in `primeqa/test_management/step_schema.py:9–16` and
`primeqa/execution/executor.py:367–424`. This is a shallow convention —
the AI generator sets `expect_fail: true` on a step, and the executor
interprets a Salesforce rejection as `expected_fail_verified`. It is explicitly
the "v2 failure mode" that Substrate-3's grounded-negative discipline is
designed to supersede: there is no grounding of the assertion against a specific
org constraint.

The `no-admissible-negative-scenario-found` refusal kind from D-083 has no
runtime counterpart yet. Substrate-3 implementation is Phase 2 (not started).

**Nothing uncommitted or untested** in this area; the existing implementation
is complete for its spec. The gap is between the current spec and the new
architecture.
