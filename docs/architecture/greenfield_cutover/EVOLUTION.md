## 2026-06-03 — Cutover opened + designed, docs-led (D-145 / D-146)

The greenfield cutover — where the substrate spine (S1–S8) replaces the live v1 product and the v1 `meta_*` tables are dropped — was, until now, **undesigned** (its intent scattered across D-012 / D-065 / D-074 / D-111 / D-134) and **not executable as one phase** (verified: `meta_*` is the live store; the S1 sync writer exists but has no production trigger; no `meta_*`→S1 migration; the substrate outputs aren't surfaced in the product). Phase 7 opened it **docs-led** (mirroring how S5 opened, D-134): author the missing design + sequence it, at zero production risk, so the cutover then runs slice-by-slice off the design.

**The SPEC (D-145).** `SPEC.md` consolidates the v1→substrate **disposition map** (REPLACE/ABSORB/DROP/MIGRATE/RELOCATE/RETIRE/STAY, each row D-cited), fixes the **migration strategy** (greenfield **re-sync** from Salesforce, *not* a `meta_*`→S1 backfill — D-012), reconciles the **schema topology** (the realized per-tenant alembic schema — D-015 built; D-023's "begins in public" milestone superseded), and the **non-goals** (the MIGRATE tables → post-cutover; `llm_calls` stays; S4 F2/F4–F7 + the S8 mechanics not cutover-blocking). It also reconciles the terminology: D-012's "Phase 4 cutover" and "the Phase-7 greenfield cutover" name the same event.

**The SEQUENCE (D-146).** `SEQUENCE.md` lays out the cutover as **ordered, gated steps** — reversible-before-irreversible, additive-before-substitutive — each with an entry-gate / exit-gate / rollback, and the one irreversible act (the `meta_*` drop) **strictly last**, gated on a clean parallel-run window + S1 verified as the prod data source: *S1-sync prod trigger → relocations → additive substrate consumers → v1 read-path switch (flagged) → parallel-run validation → `meta_*` drop*. Every "deferred to the cutover" item across the substrate docs (S5 relocation + forward-seam, D-134; S6 UI consumer + clustering dashboard, D-137; GO/NO-GO folding, D-111; the S3-ledger retirement, D-074) is folded into the step it belongs to — the ~dozen scattered deferrals become one tracked checklist (the SEQUENCE coverage table).

**Boundary.** Docs only — no code, no migration, no v1 behavior change (inert deploy). The cutover *execution* is deferred to later phases, each running one gated step. On `phase-15-greenfield-cutover` (D-147 close).

## 2026-06-04 — Step 0 executed: the S1-sync production trigger (D-150–D-154)

The cutover's **hard prerequisite** — making S1 the *live* metadata source. The S1 sync engine (`SyncEngine.run_sync`, all 11 phases Object→Flow) was **finished but dormant**: unit + integration tested, **zero production callers**. Step 0 was therefore "wire a trigger to a finished engine," not "finish the engine" — no engine/phase edits, across four slices + close:

- **S0.1 (D-150) — the seams.** `connected_orgs.environment_id` (the missing environment→sync-target link — `connected_orgs` had no link to `environments` and was never INSERTed in prod) + `resolve_sync_sf_client` + `ensure_connected_org_for_environment`. The credential path **reuses v1's** `_oauth_token` (exactly S4's `credentials.py` path) and **pre-seeds** the engine's refresh-token-grant `SalesforceClient` with the resolved access token via a new additive `access_token` param — the grant mismatch (engine wants refresh-token; v1 yields a bare access_token) resolved without touching v1's auth or the engine's transport.
- **S0.2 (D-151) — the queue.** `s1_sync_jobs` + `SyncJobStore`, a near-mechanical mirror of `s4_execution_jobs`/`ExecutionJobStore` **minus the attempts table** (the engine writes its own `sync_runs`; `last_sync_run_id` is the resume anchor). Idempotency is the S4 repeatable shape (partial-unique on the active set, keyed on `connected_org_id`); the reaper's 45-min timeout exceeds the longest sync.
- **S0.3 (D-152) — the consumer.** Claim → resolve creds → `run_sync` → complete/fail, mirroring `generation/consumer.py` with two engine-driven divergences: the terminal decision **reads `sync_runs.status`** (the engine captures phase failure in the row + returns the id; only fatal infra raises), and **resume-on-reap** (chosen at the fork over fresh-re-sync) is realized by **carry-forward** — `create_or_get_job` seeds a new job's anchor from the org's most-recent *incomplete* `sync_run` (the durable resume source of truth; at most one per org, so cleaner than the mid-run capture first floated), and the consumer passes it as `run_sync(resume_sync_run_id=…)`.
- **S0.4 (D-153) — the cadence + wiring.** The enqueuer (`run_s1_sync_enqueuer_tick`: per tenant, enqueue orgs with `environment_id` set + no active job that either carry an incomplete sync (resume) or have no sync within 24 h (never/stale); idempotency dedups) + the scheduler ticks (`s1_sync_enqueuer_tick`/`s1_sync_reaper_tick`, mirroring `s3/s4_reaper_tick`) + the worker consumer tick (`s1_sync_tick` + `_default_s1_sf_client_resolver`, mirroring `s4_execution_tick`). The loop runs end-to-end: enqueue → consume → reap.

**Boundary + deferral.** Additive — 2 tenant migrations (`20260604_0010`/`0020`) + new `primeqa/sync/{credentials,jobs,consumer}.py` + thin scheduler/worker wiring; **no engine/phase edits, no v1 behaviour change.** 29 governance tests (a stubbed `SalesforceClient` + a fake engine — no live SF), app/worker/scheduler import green. **The exit-gate's live-SF half is unavoidably ops-deferred** — a real `run_sync` → `entities`/`edges`/`sync_runs`/`ai_enrichment_queue` rows + the `meta_*` parity probe needs SF creds + ~30 min (the `@pytest.mark.sandbox` e2e suites). So Step 0 lands **built + governance-tested**; S1-goes-live is the ops run. Standing follow-ons: the ops live-SF proving; the prod-migration applies (`20260604_0010`/`0020`). On `phase-17-cutover-step0-s1-sync-trigger` (D-150–D-154 close).

## 2026-06-04 — Step 2 executed: the additive substrate-insights surface (D-155–D-157)

The cutover's third executed step — making the dormant substrate outputs **visible additively** in v1 (no v1 removal). Two slices delivered the goal; two planned slices hit a verified premise break + deferred.

- **2.1 (D-155) — the read surface.** A standalone `/substrate-insights` page surfaces S6 interpretations + cross-run clustering + S8 grounding-validity. The **first v1→substrate read consumer**: v1 owns the bridge (`primeqa/intelligence/substrate_insights.py` — `get_substrate_insights` opens `Session(bind=get_tenant_connection(tid))`, since the read APIs need an ORM Session), best-effort (`available=False` on any error, never breaks the page), wrapping a pure `_assemble_insights` (testable on the rollback fixture). **Standalone — keyed on substrate ids — because v1 run ids ≠ substrate run ids.** Empty-state is a first-class branch (every store is empty until Step 0's live-SF run). Role-gated `view_intelligence_report` (the role→set map is counterintuitive — ba + admin + superadmin, not viewer/tester). 35 governance tests.
- **2.2 (D-156) — the S5→S3 forward-seam settled (not wired).** The one open architectural question Step 2 carried (D-134's deferral). Resolved: the generation direction settled as "v1 generation stays as the product's authoring path (data-source REPLACE onto S1); S3 is parallel + downstream-only, **not** product-facing"; the semantic fit between S5's test-authoring knowledge and S3's claim-emitter is ~zero. Decision: **don't wire** — revisit only if a future decision makes S3 product-facing.
- **2.3 + 2.4 — deferred to Steps 3–4 (a verified premise break).** Grafting an S6 panel onto `/runs/:id` (2.3) + release-grain clustering (2.4) both need a v1-run↔substrate-run correlation. The data model **lacks it**: v1 `test_cases` carry no S2-claim reference; `s4_execution_runs`/`s6_interpretations` carry no v1 reference; the two execution worlds are disjoint (no shared key, no write-path) — consistent with D-156's separate-generation-paths finding. The correlation requires unifying v1+substrate execution, which is the flagged read-switch (Step 3) / parallel-run (Step 4), not additive Step 2. Folded into those steps.

**Boundary + deferral.** Additive — a new v1 bridge module + a read-only route + template + sidebar entry; **no migration, no substrate-package change, no v1 behaviour change.** 35 governance tests; app imports. The page's **live data** + the **parity-of-meaning review** are ops-deferred (every substrate store is empty until task #119's live-SF run — the same live half as Step 0). On `phase-18-cutover-step2-substrate-consumers` (D-155–D-157 close).

## 2026-06-04 — Step 3 executed: the flagged v1 metadata read-switch to S1 (D-158–D-162)

The substrate starts **serving** the product: v1's metadata *reads* route to the S1 semantic org model behind the per-tenant `cutover_read_s1` flag, with `meta_*` as the flag-off fallback — the start of the parallel run. Reversible (flip the flag), additive (default off → v1 unchanged). Five slices on the now-familiar build-ahead-behind-a-flag pattern (Steps 0/2): built + governance-tested now, live dual-stack parity ops-deferred (S1 is empty in prod until #119).

- **3.1 (D-158) — the seam.** `MetadataAccessor` (`primeqa/metadata/accessor.py`) implements the `meta_*` read-interface (`get_objects`/`get_fields`/`get_validation_rules`/`get_object_by_api_name`), reads the `cutover_read_s1` flag (migration `051`, public `tenant_agent_settings`) tolerantly, and routes `flag AND s1_reader ? S1 : meta_*` — everything else `__getattr__`-delegates to the repo. Wired at the 3 call sites with `s1_reader=None` (pure passthrough): **zero behaviour change.**
- **3.2 (D-159) — the generation reader.** `MetadataS1Reader` (`primeqa/metadata/s1_reader.py`) eager-hydrates one org's metadata from the S1 query interface (`get_entities`/`get_related`/`get_entity_details`) into frozen `_S1Object`/`_S1Field`/`_S1ValidationRule` duck-types, deterministic ordering; best-effort builder (empty/error S1 → `None` → `meta_*`). Flag-on → generation context reads S1. `meta_version_id` args are ignored (the snapshot is pinned to the S1 `version_seq` it hydrated at — the one intentional asymmetry).
- **3.3 (D-160) — the first sync-engine touch.** Additive `field_details.is_createable`/`is_updateable` (alembic tenant `20260604_0030`, default `true` = SF-permissive, no backfill) + a 2-line `_map_field_details` change (the describe already fetches `createable`/`updateable`; they survive normalization). Gives the validator the per-field writability its `field_not_createable` (CRITICAL) / `field_not_updateable` (WARNING) checks need.
- **3.4 (D-161 + D-161.1) — the validator/linter reader, at true parity.** The 3 validator-construction sites flip to `with_s1_reader=True`; the picklist 2-hop (`field_details.picklist_value_set_entity_id` → `get_picklist_values` → the `value_api_name` list) reaches `picklist_value_not_allowed` (WARNING). **A mid-impl premise break (D-161.1), surfaced as a HOLD + root-caused:** S1 stores a field's `sf_api_name` object-qualified (`_extract_external_id`'s `{parent}.{name}` → `Account.Name`) where v1 `meta_*` + every test step use the bare name (`Name`). The reader passing the qualified name through would have raised `field_not_found` CRITICAL on *every* field; the fix strips the parent prefix in the reader (the exact inverse), correcting both the validator and the already-shipped 3.2 generation context. The 3.2 "parity" test — which had only asserted the reader's self-consistent output (never compared to `meta_*`) — was corrected to bare names, and a validator-over-reader parity test added (each rule fires off a real S1 snapshot with bare-name steps).
- **3.5 (D-162) — close.** GAP-2 ratified: **preflight stays on `meta_*`** (its `MetaSyncStatus` per-category health + `MetaVersion.completed_at` staleness have no clean S1 map; `meta_*` is populated through Steps 3–4 so preflight reads correctly) — its S1 cutover is relocated to a **Step-5 prerequisite** (the `meta_*` drop can't proceed while preflight reads `meta_*`).

**Boundary + deferral.** Additive — a new accessor + reader + the `cutover_read_s1` public flag (migration `051`) + the additive `field_details` CRUD columns (tenant `20260604_0030`); **flag-off → zero v1 behaviour change.** 128 governance tests (semantic reader + validator-parity + accessor/mapper units), app imports. The **live dual-stack byte-parity** (real-org S1 vs `meta_*` for the pilot tenants) is ops-deferred with #119 — the same live half as Steps 0/2. Standing prod-migration applies: `051_cutover_read_s1_flag.sql` (public) + `20260604_0030_field_details_crud_flags` (tenant). On `phase-19-cutover-step3-read-path-switch` (D-158–D-162 close).
