# B0.1 — Exact-label affinity in grounded-recovery ranking (design note)

**Status: IMPLEMENTED + LIVE-VALIDATED on branch
`phase-7-substrate-3-b01-label-affinity` (follow-up to D-362, opened on
Slice-1 acceptance / D-363). Scope: `generation/recovery.py` ranking order
only. Six consecutive req-320 runs: 6/6 converged, FL01 identity `a23b2a5f`
in all six; VR-benchmark regression pair (main vs branch, req-315): zero
recovery offers on both sides — the ranking path never executes there —
and identical 10/10 coverage. One amendment found at implementation
(single-token labels earn no phrase bonus, §Proposal).**

## Problem

When a proposed reference misses and B0 assembles a candidate offer, the
ranking blends guess-similarity with a requirement-context token term. Both
terms are deterministic, but neither recognizes that a candidate's **exact
business label** appears verbatim in the requirement text — the strongest
grounded relatedness signal available. Incidental token overlap can therefore
outrank the requirement's own entity.

Live instance (Slice-1 validation, run `44178a2b`, guess `Order__c` against
req-320): the offer ranked `PLS_FB_Order_Line__c` (its "line" token matches
the unrelated "line items" sentence), a packaged `Service_Order`, and the
standard `Order` — while `PLS_FB_Order__c`, whose label **"PLS FB Order"
appears verbatim in the requirement**, scored 4th and fell off the 3-candidate
limit. The model followed the offer and anchored wrong (honest refusals, zero
claims — fail-closed held, but the run did not converge). A second live
instance landed on the PRODUCTION path immediately after the Slice-1 merge
(run `c9c6fc99`, deployed worker, v29): same trajectory, 15/15 honest
refusals, zero claims. This is the single residual convergence-variance
driver after prompt v29 (post-v29 tally: 5 of 7 runs converged; both misses
are this trajectory).

## Proposal

Add a third, deterministic term to `rank_candidates` — an **exact-label
affinity bonus** applied *after* pool admission:

- `phrase_tokens(candidate) = token-count of the candidate's display_name`
  **iff** the whitespace-normalized, case-insensitive label occurs in the
  requirement text at word boundaries (alphanumeric-boundary regex; no
  stemming, no distance, no fuzz); else 0.
- **Amendment (found at implementation): single-token labels earn no phrase
  bonus.** One-word labels ("Record", "Order", "Case", "Task") are exactly
  the common-noun ambiguity class — they occur in ordinary requirement prose
  without naming the entity, and when such a label is the pool's only hit,
  the pool-relative normalization would hand it the full bonus (live
  counter-example: label "Record" against prose "the record of the beta
  stream…" jumped a more-related candidate). The exact-label signal this
  term exists for is MULTI-WORD verbatim presence; the live fix ("PLS FB
  Order", 3 tokens) is unaffected, and one-hit-wonder pools stay
  byte-identical to pre-B0.1.
- `score' = score + 0.5 × phrase_tokens / max(phrase_tokens over the admitted
  pool)` — the same in-pool normalization the context term already uses, so
  longer verbatim labels ("PLS FB Order", 3 tokens) outrank shorter contained
  ones ("Order", 1 token).
- Sort by `(-score', sf_api_name)` — the existing total order.

## Properties (the B0.1 contract)

- **Deterministic**: pure string test + arithmetic; same total order as today.
- **Benchmark-independent / metadata-driven**: consumes only `display_name`
  (S1 metadata) and the run's own requirement text; no org- or
  benchmark-specific vocabulary anywhere.
- **No fuzzy matching**: exact word-bounded substring after whitespace/case
  normalization only.
- **Existing behaviour preserved**: admission is unchanged (the similarity
  threshold still gates the pool *before* the bonus), so no new entities are
  ever exposed; when **no** admitted candidate's label appears in the text,
  every `phrase_tokens` is 0 and the ranking is **byte-identical** to today
  (all engine call sites without `context_text` are untouched by
  construction).

the shipped function's live output.

## Expected impact

The one non-converged Slice-1 validation run took exactly this offer's #1
candidate. With the true object ranked #1 (and the offer's instruction text
unchanged), the same trajectory converges — estimated **5/6 → 6/6** on the
frozen benchmark, with the caveat that model choice is stochastic: the bonus
makes the offer *correct*, it cannot force the pick. No other live behaviour
changes (order-only, admission-identical, telemetry/message formats
untouched).

## Tests to pin (when implemented)

1. The live trajectory: guess `Order__c` + req-320-shaped text + a pool
   containing the four objects above → true object first.
2. No-phrase pool → ordering byte-identical to the pre-B0.1 function.
3. No `context_text` → unchanged.
4. Word-boundary honesty: label "External Ref" does NOT match "External
   references"; label "Order" DOES match "an order raised".
5. Determinism under pool permutation (existing invariant, extended).

## Exit gate (when implemented)

Three convergence runs on the frozen benchmark from the branch: 3/3
converged, FL01 identity unchanged (`a23b2a5f`-class), zero false tests —
plus the full offline tree green with the pinned no-phrase byte-identity test.
