### Classification key (the decisive field)
- **[MECHANICAL]** — unambiguous root-cause fix: a guard/decorator/index/config change or a fix with an in-repo template; no substrate-identity or irreversible consequence. **Claude Code can execute it to a HOLD.**

Options + a lean are given; the owner (and TA where flagged) decides. **When unsure, defaulted to NEEDS-DECISION** — over-flagging is safe.

### Security (SEC)

#### SEC-1 — Any authenticated user (even viewer) can read fully-decrypted SF/Jira/LLM secrets via GET /api/connections/&lt;id&gt;, which is role-gated nowhere.

`primeqa/core/routes.py:322-330 (route def line 322; svc.get_connection call line 327)` · **High** · Wave 1 · **[MECHANICAL]**

- **Root cause.** The API detail route is decorated `@require_auth` only (no tier gate), and its service call returns decrypted config verbatim: routes.py:322-327 `@core_bp.route("/api/connections/<int:conn_id>", methods=["GET"]) / @require_auth / def get_connection(conn_id): ... conn = svc.get_connection(conn_id, request.user["tenant_id"])`; service.py:413-414 `def get_connection(...): return self.conn_repo.get_connection_decrypted(...)`; repository.py:363-390 decrypts every sensitive field (`client_secret`,`password`,`api_token`,`api_key`,`voyage_api_key`) into `config` and returns it. `require_auth` (core/auth.py:58) defaults missing role to `viewer`, so no role is enforced — asymmetric with the web twin `connections_detail` (views.py:1493) which is `@role_required("admin")` and the mutating API routes (create/delete/test all `@require_role("admin")`).
- **Fix.** Change the route decorator from `@require_auth` to `@require_role("admin")` to match the sibling mutating connection routes and the web detail twin, AND mask secret fields in the HTTP response even for admins (return the redacted `_conn_dict` shape for API display, reserving `get_connection_decrypted()` for server-side credential resolution in sync/execution/worker). The route already imports the same pattern used at routes.py:305/336/349.
- **Template to follow.** primeqa/core/routes.py:335 delete_connection (sibling @require_role("admin") on the same conn_id resource) for the decorator; primeqa/core/service.py:490 ConnectionService._conn_dict for the redacted response shape
- **Blast radius.** Read-only endpoint; touches the connections API surface only. Adding the gate rejects viewer/member callers (intended). Masking the response could break any UI/consumer that currently reads decrypted config over this API — grep shows the web detail view uses svc.get_connection server-side (not this API), so client impact is expected to be nil, but any JS/HTMX fetch of /api/connections/&lt;id&gt; must be checked. _(touches: auth-path)_
- **Proof.** New tests/integration/test_connection_authz.py: (a) a viewer-token GET /api/connections/&lt;id&gt; returns 403 (not 200); (b) an admin-token GET returns 200 but the JSON `config` contains no plaintext secret (client_secret/password/api_token/api_key absent or masked). Assert both the tier gate and the response masking. — ⛔ no collectable test yet — must be written.

#### SEC-2 — GroupService.add_member / add_environment validate the group against the caller's tenant but never tenant-scope the client-supplied user_id / environment_id, so an admin can link a foreign tenant's user or environment into a group and disclose their PII / org URL via the group detail view.

`primeqa/core/service.py:537 (add_member), :549 (add_environment); callers pass client JSON at core/routes.py:426,455 and views.py:1747,1776; disclosure surface get_group_detail core/service.py:527-530` · **High** · Wave 1 · **[MECHANICAL]**

- **Root cause.** The guard checks the WRONG id: `group = self.group_repo.get_group(group_id, tenant_id) ... self.group_repo.add_member(group_id, user_id, added_by)` — the group is tenant-checked but `user_id` (from `data["user_id"]` at routes.py:426) is written straight through. `group_members` / `group_environments` carry no tenant column (models.py:256-287), so nothing downstream re-scopes it; get_group_detail then emits the foreign user's email/full_name and the foreign env's sf_instance_url (core/service.py:527-530). Same class as the release/service.py add_requirement fix, which already documents this exact join-table-has-no-tenant-column hazard.
- **Fix.** In add_member, before add_member repo call, verify the user belongs to the caller's tenant: `own = self.group_repo.db.query(User.id).filter(User.id==user_id, User.tenant_id==tenant_id).first(); if not own: raise ValueError("User not found")` — and the mirror for add_environment with Environment.id / Environment.tenant_id. Both User.tenant_id (models.py:40) and Environment.tenant_id (models.py:87) exist, so the filter is direct. remove_member/remove_environment are lower risk (they only unlink an already-attached row) but the same guard closes the whole surface.
- **Template to follow.** primeqa/release/service.py:103-121 (add_requirement — verbatim sibling: tenant-scope the client-supplied linked id before writing a tenant-less join row)
- **Blast radius.** Touches the two group-membership write paths only (API + web routes). No schema change. Risk: none beyond turning previously-accepted cross-tenant/nonexistent ids into a ValueError('… not found'); legitimate same-tenant links are unaffected. The remove_* pair could optionally take the same guard for symmetry. _(touches: auth-path)_
- **Proof.** New sibling test in tests/integration/test_tenant_isolation.py modeled on test_add_requirement_tenant_scoped (line 197): create a group in tenant A, call GroupService.add_member(group_id, TENANT_A, foreign_user_id_from_tenant_B, uid) and assert it raises ValueError; then assert a same-tenant user_id succeeds. Mirror for add_environment. — ⛔ no collectable test yet — must be written.

#### SEC-3 — SSRF: server issues an authenticated request attaching the org's decrypted access-token to whatever host the admin put in sf_instance_url (no scheme/host/private-IP validation).

`primeqa/core/service.py:336 (outbound call) + primeqa/core/service.py:283/291 (write-time store, create_environment)` · **High** · Wave 1 · **[MECHANICAL]**

- **Root cause.** sf_instance_url is stored with only a non-empty check and never scheme/host/allowlist-validated, then interpolated raw into an authenticated GET. Store: `if not sf_instance_url:` (service.py:283) is the ONLY check; call: `url = f"{env.sf_instance_url.rstrip('/')}/services/data/v{env.sf_api_version}/"` then `http_requests.get(url, headers={"Authorization": f"Bearer {creds['access_token']}"}, timeout=15)` (service.py:336-340). Grep for urlparse/ipaddress/169.254/is_private/validate_sf_instance_url/allowlist across service.py+routes.py+worker_runner.py returns nothing.
- **Fix.** Add a single validate_sf_instance_url() guard (require https scheme, resolve host and reject RFC-1918 / loopback / link-local 169.254.169.254 / ULA, allowlist *.salesforce.com / *.force.com / *.lightning.force.com). Enforce it at write time in create_environment (service.py:265-291, where the non-empty check is) AND before the outbound call at service.py:336. Reuse the SAME helper for SEC-5 and SEC-P4.
- **Blast radius.** Touches every Salesforce test-connection and, transitively, the shared validator SEC-5/SEC-P4 will reuse. A too-tight allowlist could reject legitimate custom My-Domain / sandbox instance URLs; must cover *.my.salesforce.com and *.lightning.force.com. Admin-gated route (@require_role("admin") at routes.py:249) narrows the attacker set to a tenant admin, but the token exfil is real. _(touches: auth-path, live-write-path)_
- **Proof.** New tests/unit test: validate_sf_instance_url('http://169.254.169.254') and ('https://evil.example.com') raise/return-invalid; ('https://acme.my.salesforce.com') passes. Plus a create_environment test asserting a private-IP/non-https/non-allowlisted URL is rejected at write time. — ⛔ no collectable test yet — must be written.
- **Dependencies.** none (SEC-5 and SEC-P4 depend on this finding's validate_sf_instance_url() helper)

#### SEC-4 — POST /releases/&lt;id&gt;/run enqueues live substrate runs against any accessible environment — including production — with no is_production gate, so any Member (ba/tester) can trigger mutating recipe runs against a production org.

`primeqa/views.py:3506-3566 (releases_run)` · **High** · Wave 1 · **[MECHANICAL]**

The docstring states the async production decision is therefore 'made at the enqueue boundary instead' — but this enqueue boundary omits it. The route never reads env.is_production nor a confirm_production field, unlike the sibling enqueue boundaries.
- **Fix.** Before enqueue, add the same two-part production gate the sibling async enqueue path uses: (1) fail closed for non-Admins on env.is_production — `if env.is_production and rank(request.user.get("role")) < Tier.ADMIN: flash+redirect`; (2) read a confirm_production form field and call `ok, msg = environment_can_bulk_run(env, confirm_production)`, refusing on not-ok. env is already loaded at views.py:3532, so this is a pre-enqueue insertion with no new query. Add the confirm_production checkbox to the run form template.
- **Template to follow.** primeqa/views.py:3280-3286 (api_s4_execution_enqueue — the sibling async enqueue boundary: env.is_production + rank<Tier.ADMIN fail-closed, then environment_can_bulk_run(env, confirm_production)); gate helper primeqa/runs/bulk.py:40 environment_can_bulk_run
- **Blast radius.** Touches the web release-run form (adds a confirm_production checkbox) and the releases_run handler. Behavioral change: Members can no longer enqueue against production envs; existing sandbox/non-prod runs unaffected (environment_can_bulk_run returns True when is_production is false). No schema, no downstream change (enqueue_claims_for_requirements signature unchanged). Risk: if the run.html template's env dropdown offered prod to Members, they lose that path (intended). _(touches: live-write-path, auth-path)_
- **Proof.** New integration test tests/integration/test_release_run_prod_gate.py: as a Member (tester role) POST /releases/&lt;id&gt;/run with environment_id pointing at an is_production env and no confirm_production → assert redirect/flash 'Production org confirmation required' (or Admin-required) and assert zero s4_execution_jobs rows enqueued; then as Admin with confirm_production=true → assert enqueue succeeds. Mirror the existing confirm_production assertions in tests/test_s4_execution_jobs.py:171-178. — ⛔ no collectable test yet — must be written.

#### SEC-6 — read_org_model builds the S1 reader with no connected_org_id, so on a multi-org tenant the /org-model metadata browser renders the org-blind UNION of every connected org's objects/fields/validation rules instead of one org's model.

`primeqa/metadata_bridge/s1_sync_console.py:301 (SemanticOrgModel(conn) — no org); consumed by the /org-model route views.py:1005-1014, read at views.py:1012` · **Low** · Wave 4 · **[NEEDS-DECISION]** · **needs TA** · theme: **per-org-isolation**

- **Root cause.** `return _read_org_model(SemanticOrgModel(conn), object_api_name)` constructs the reader with only the connection. SemanticOrgModel's constructor (semantic/query.py:206-210) takes an optional `connected_org_id` whose docstring (query.py:193-203) states `None` = the legacy org-BLIND behavior — every read sees the whole tenant model. - **Fix.** Two paths (see decision_options).
